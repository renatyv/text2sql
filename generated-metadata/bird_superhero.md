# Additional Metadata

## Clarified Semantics

- `superhero` (750 rows) is the fact/grain table: one row per hero, id range 1..756 with gaps (ids above 750 and missing ids exist), so join on the FK values, not on id arithmetic.
- `hero_attribute` vs `hero_power` are both many-to-many bridge tables keyed to `superhero.id`, but their row grain and coverage differ. `hero_attribute` (3738 rows) covers 623 of 750 heroes and stores exactly 6 rows per covered hero (one scalar `attribute_value` 5..100 per `attribute` Intelligence/Strength/Speed/Durability/Power/Combat) — it quantifies the six combat attributes for every hero it covers. `hero_power` (5825 rows) is a pure membership list over a 167-row `superpower` dimension: 652 heroes covered with ~9 powers each (no count fixed per hero). Use `hero_attribute` when comparing numeric hero ratings across the six attributes; use `hero_power` when testing presence/absence of named abilities. 38 heroes have neither table.
- The three colour FK columns (`eye/hair/skin_colour_id`) all target the single `colour` dimension. However `colour` has 35 rows while `skin_colour_id` only uses ids 1..33 and eye/hair use subsets up to 35; treat each FK as its own subset of the shared gloss and don't assume the same colour maps to the same bodily feature usage.
- `full_name` (483 distinct) is null for 122 heroes and not unique per hero; `superhero_name` (743 distinct, ~7 duplicates) is the better label key. `alignment_id`, `publisher_id`, `race_id` may be null (6/3/4 nulls respectively), so joins/existence checks must be outer-tolerant.
- `height_cm`/`weight_kg` include real zeros (155 and 172 rows) and extreme outliers (weight up to 90,000,000, height up to 30,480) — treat 0 and extreme values as missing/garbage for aggregates, and consider log/median handling.
- Dictionary tables (`alignment` 4, `gender` 3, `publisher` 25, `race` 61) are small complete sets; every `race` and `publisher` id is referenced by at least one hero, so no dangling dimension rows.

## Potential Join Strategies

- `hero_power` → `superpower` → join heroes to ability names: `hero_power.power_id = superpower.id`, filter on `power_name`. Cardinality is many-to-many (avg 8.9 powers/hero); every `superpower.id` is used, so no dead-power filtering needed.
- `hero_attribute` → `attribute` by `attribute_id` to pivot the six rating column values (e.g., filter `attribute_name = 'Durability'`). Covered heroes always have all 6 rows, so a self-join/pivot without left-join is dense; joins limited to the 623 covered heroes miss the other 127.
- `superhero` → `hero_power` → `superpower` and separately `superhero` → `hero_attribute` → `attribute` cross-connect realms: linking the same hero's attribute ratings and power list requires joining both paths on `superhero.id`. 563 heroes appear in both; 38 in neither — a full-outer/EXISTS approach is needed to avoid dropping hero-only or no-metric heroes.
- Three-way colour join: `superhero` joined to `colour` three times via distinct alias keys (`eye_colour_id`, `hair_colour_id`, `skin_colour_id`) to get three name columns from the same cardinal dim table.
- `superhero.alignment_id`/`publisher_id`/`race_id` → dimension tables are straightforward 1:N (giving each hero at most one group); all referenced dimension rows are populated, so inner joins do not drop dimension rows but outer is required because 6/3/4 hero rows carry nulls.
