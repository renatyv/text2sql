# You gave the agent everything it needed — and it didn't help

Everyone says text-to-SQL fails because the model doesn't know your database. So I handed a coding agent a complete, pre-generated profile of the schema — every table, every column, value distributions, sample rows — and measured what happened. Spoiler: **accuracy didn't budge, tokens exploded ~6x, and the agent stopped thinking for itself.** If you're building RAG-over-schema, feeding DDL dumps, or paying to stuff database context into prompts, this is the $40 experiment that might save you a lot of money.

Feeding a complete database profile from [db-snooper](https://github.com/renatyv/db-snooper) to a coding agent did not improve its text-to-SQL accuracy.

## Testing on BEAVER benchmark data (3 databases, 100 questions each)

- **Accuracy didn't change.** Across all three databases the number of nailed queries was within noise (every pairwise McNemar test p = 1.0, except one p = 0.5):

| Database | Raw | + Profile | + Metadata |
|---|---|---|---|
| neutron | 13% | 13% | 13% |
| nova | 9% | 8% | 11% |
| dw | 5% | 4% | 3% |

- **Input tokens grew ~6x** (pooled across runs) — the full profile is re-supplied in context, and on the biggest database it alone costs ~9x more per run than the raw arm
- **Turns dropped from ~4.6 to ~2.2, database queries from 7.8 to 1.3.** The agent read the profile, nodded, and stopped asking questions. It was just wrong sooner.

## The third arm: metadata instead of the full profile

The profile is huge (1,200–4,000 lines of schema, statistics, and sample values per database), so I added a third arm: give the agent a small **aggregated metadata** document instead — a quarter of the tokens, and accuracy was just as (un)changed.

The metadata was generated by the same coding agent, in the same sandbox, from two artifacts:

1. **The db-snooper profile** — `db-snooper profile` against MySQL produces per-table schema (columns, types, indexes, FKs), inferred relationships, per-column value distributions, and sample rows.
2. **Schema links** — deterministic linking hints: declared foreign keys from `information_schema` plus same-name column candidates (excluding noise like `id`, `created_at`), grouped into "declared" vs "inferred" join paths.

A one-off pi agent run (12 turns, same OpenRouter-only egress proxy, same SELECT-only account, no access to benchmark questions or answers) read both files and wrote a short `<db>.md` with two sections: **Clarified Semantics** (e.g. "LBaaS v1 and v2 tables coexist; the `standardattributes` table is the shared backbone") and **Potential Join Strategies** (join predicates with cardinality caveats). That file — 26–43 lines — is what the `metadata` arm got. A fourth arm with both profile and metadata exists in the harness, but the headline run used three.

## [How I tested](https://github.com/renatyv/text2sql)

- Three MySQL database dumps from [BEAVER benchmark](https://huggingface.co/datasets/BeaverBench/beaver): neutron, nova, dw
- 100 questions per database per arm (seed-fixed sample). Real execution accuracy, scored against gold results.
- a coding agent (pi) driving GPT-5.6 Luna PRO via OpenRouter, effort=medium
- Fresh Docker container per question, a SELECT-only database account, access to the DB and the OpenRouter endpoint only
- Maximum 15 turns per query
- Spent about $20 for the final run, plus $20 while preparing the benchmark harness

## Original BEAVER bench

- hand-coded agents in Python
- reasoning=off
- the model is fed pre-retrieved/reranked tables (Qwen embedding top-50 / reranker top-15), and settings 1/2 add gold schema-linking and domain-knowledge hints

## Pitfalls and bad ideas encountered

- pi silently defaults to a 128k context for unknown models
- Unknown model slugs report zero projected cost until their rates are added to `harness/openrouter_models.json`
- OpenRouter's usage object carries no cost
- Telling the agent to LIMIT 5 exploratory queries is BAD. The model appended LIMIT 5 to its final SQL, tanking execution accuracy.
- Restricting queries to 100 rows is BAD. Some of BEAVER's gold queries return 1000s of rows. Ouch!
- Agents never returned SQL. Fix: the prompt reserves the final turn for the answer and steers `return the fucking query now!` on the penultimate turn.
